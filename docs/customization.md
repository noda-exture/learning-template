# 公開後のカスタマイズ・更新手順

自分のCloudflareへの初回公開が終わり、サイトが正常に表示・操作できることを確認した後に使う手順書です。まだ公開していない場合は、先に[導入・初回公開の手順](cloudflare.md)を進めてください。

## この手順の使い方

まず「1. 編集して公開先へ反映する共通手順」を確認し、変更したい項目へ進みます。以下のパスはすべて、**自分用にクローンしたプロジェクトのフォルダを基準**にしています。

| 変更したいもの | 編集するファイル・フォルダ | この手順書の項目 |
| --- | --- | --- |
| 商品名・説明・色・サイズ・価格 | `public/catalog.mjs` | [2. 商品情報](#products) |
| 静的HTMLページ | `public/lab/` | [3. 静的ページ](#static-pages) |
| head・bodyの共通タグ | `config/tags/head.html` / `config/tags/body-start.html` | [4. 共通タグ](#shared-tags) |
| 既存の検証用Cookie | `config/lab.mjs` | [5. Cookie](#cookies) |
| 別のCookieの追加処理 | `src/app.mjs` | [5. Cookie](#cookies) |
| 同意バナー・設定・保存期間 | `public/cmp-config.mjs` など | [6. 同意設定の検証](#consent) |
| GitHubの配布元から更新を取得 | コマンドで取得します。 | [7. 配布元の更新](#upstream-updates) |

ターミナルを開き直した場合は、`cd "プロジェクトのフォルダの絶対パス"` で移動します。`ls` を実行して `package.json` が見えることを確認してください。初回のクローン・`cf:setup`・サブドメイン登録をやり直す必要はありません。

コマンドは1行ずつ実行し、成功してから次へ進みます。Windowsで `npm.ps1` の実行が禁止される場合は、`npm` を `npm.cmd` に置き換えます。

## 1. 編集して公開先へ反映する共通手順

編集前に、変更するファイルのコピーをプロジェクトの外に保存しておくと、戻したい場合に比較できます。

**自分のPCでファイルを修正したら、保存して `npm run cf:deploy` を実行するとCloudflareへ反映できます。** プロジェクトのフォルダ内で実行します。HTML・CSS・タグの編集だけであれば、毎回 `git pull` や `npm ci` を実行する必要はありません。GitHubへpushしなくても、PC上の保存済みファイルを公開できます。

```sh
npm run cf:deploy
```

`public/lab/` のHTMLや `config/tags/` の共通タグも、ファイル保存だけでは公開先に反映されません。デプロイ時にビルドと静的ページ一覧の生成も行います。成功後、公開URLを再読み込みします。

## 2. 商品情報・色・サイズ・価格を変更する

### どのファイルの、どこを編集するか

**自分用にクローンしたフォルダの `public/catalog.mjs` をエディタで開きます。** 例えばクローン先が `my-learning-store` なら、`my-learning-store/public/catalog.mjs` です。

現在のファイルでは、マグは3行目の `id:'mug'`、トートは5行目の `id:'bag'` にあります。行番号が変わっている場合は、エディタの検索で `id:'bag'` を探してください。一つの商品が1行にまとまっているので、その行の変更したい値だけを書き換えます。

| 変更したいもの | トートの行で編集する箇所 | 反映される場所 |
| --- | --- | --- |
| 商品名 | `name:'キャンバス トート'` の文字列 | 商品一覧・詳細・カートなどの商品名です。 |
| 商品説明 | `description:'必要なものを…'` の文字列 | 商品詳細の説明文です。 |
| 基本価格 | `price:3200` の数値 | 商品一覧の価格と、サイズ別価格の計算の基準です。 |
| 選べる色 | `id:'color'` の属性にある `values:['ナチュラル','ブラック','オリーブ']` | 商品詳細の「色」の選択肢です。 |
| 選べるサイズ | `id:'size'` の属性にある `values:['S','M','L']` | 商品詳細の「サイズ」の選択肢です。 |
| サイズごとの価格差 | `priceAdjustments:{S:0,M:600,L:1200}` の数値 | サイズ選択後の価格、カート・注文の金額です。数値は販売価格そのものではなく、基本価格への加算額です。 |
| イラストの色 | 商品直下の `color:'#9b9e7e'` | 商品イラストの表示色です。「色」の選択肢とは連動しません。 |

文字列の引用符、項目の区切りのカンマ、角括弧・波括弧は残します。価格は `4000` のように半角数字で入力し、`4,000` や `¥4000` とは書きません。商品の `id:'bag'` はカートなどの識別に使うため、名前や価格を変えるときも変更しません。

### 例：トートのMサイズだけを4,000円にする

トートの基本価格が `price:3200` の場合、Mサイズの加算額を600円から800円へ変更します。

変更前：

```js
priceAdjustments:{S:0,M:600,L:1200}
```

変更後：

```js
priceAdjustments:{S:0,M:800,L:1200}
```

この変更で **Sは3,200円、Mは4,000円、Lは4,400円**になります。`M:4000` とすると、基本価格3,200円に加算されて7,200円になるので注意してください。

保存後、クローンしたプロジェクトのフォルダ内で実行します。

```sh
npm run cf:deploy
```

成功したら、公開URLの末尾に `/classic/product/bag` または `/spa/product/bag` を付けて開き、再読み込みして「サイズ」をMに変更します。**表示価格が4,000円になれば反映完了です。** カートに追加すると、その価格で計算されます。公開済みの注文履歴の金額は変わりません。

選択肢を増やす場合も同じファイルを編集します。例えばXLを追加する場合は、サイズの `values` を `['S','M','L','XL']` にし、`priceAdjustments` に `XL:1800` を追加すると、基本価格3,200円に対してXLは5,000円になります。

### 属性設定の書き方と動作

商品情報は `public/catalog.mjs` の `products` にあります。商品ごとに `attributes` で色・サイズなどの選択肢を設定できます。例えば、既存の商品オブジェクトの価格と属性を次のように設定します（商品全体ではなく一部の例です）。

```js
price: 3200,
attributes: [
  {id: 'color', label: '色', values: ['ナチュラル', 'ブラック', 'オリーブ']},
  {id: 'size', label: 'サイズ', values: ['S', 'M', 'L'],
   priceAdjustments: {S: 0, M: 600, L: 1200}}
],
```

`id` は属性の識別名、`label` は画面の表示名、`values` は選択肢です。`id` は商品内で重複しない英数字・アンダースコアの名前にし、`values` には1つ以上の重複しない文字列を入れます。素材なども同じ形式で追加できます。選択肢が不要な商品は `attributes` を省略します。

`price` が基本価格で、`priceAdjustments` は各選択肢の加算額（円）です。上の例ではSが3,200円、Mが3,800円、Lが4,400円です。指定がない選択肢は加算0円になります。価格差が不要な属性は `priceAdjustments` を省略できます。複数属性に加算額を設定した場合は合算します。基本価格・加算額は0以上の整数にしてください。

商品詳細で選択すると表示価格も変わり、カート・注文確認・注文完了・注文履歴まで選択内容と金額を引き継ぎます。同じ商品でも色・サイズが違えばカートは別行になり、同じ組み合わせは数量を合算します。数量上限は組み合わせごとに20個です。初期選択は各属性の先頭で、従来のAPI呼び出しで選択指定を省略した場合も先頭を使います。

サンプルではマグとトートに属性を設定し、トートはサイズごとに価格が変わります。既存の `color: '#9b9e7e'` などはイラストの色指定で、購入時の色の選択肢とは別です。選択に応じた画像変更や在庫管理はありません。

属性追加前のカート・注文は選択内容なしで表示し、既存カートには基本価格を使います。注文確定前のカート価格は現在の商品設定から計算します。確定した注文は選択内容と価格を保存するため、その後商品設定を変更しても過去の注文は変わりません。

保存後、`npm run cf:deploy` で公開先へ反映します。

## 3. 静的ページを追加する

**プロジェクト内の `public/lab/` フォルダにHTMLファイルを追加します。** 例えば `public/lab/my-test.html` を作成すると、公開後は次のURLで開けます。

```text
https://<Worker名>.<登録したサブドメイン>.workers.dev/lab/my-test.html
```

URLに `public` は含めません。`<Worker名>` と `<登録したサブドメイン>` は自分の値に置き換えます。

初めて作る場合は、既存の `public/lab/welcome.html` を同じフォルダ内にコピーして `my-test.html` に名前を変え、エディタで内容を編集します。`<title>` を変更すると、静的ページ一覧に表示される名前も変わります。拡張子は `.html` にし、`.html.txt` になっていないことを確認します。

保存後に `npm run cf:deploy` を実行すると、公開サイトの `/lab/`（静的ページ一覧）にも自動で追加されます。一覧への手動登録は不要です。`public/lab/index.html` は自動一覧の予約URLに当たるため、作成しません。

## 4. 全ページ共通のhead・bodyタグを追加する

**計測タグなどを全ページに追加する場合は、次のファイルを編集します。** どちらもプロジェクト内の `config/tags/` フォルダにあります。

| 編集するファイル | 挿入される場所 | 貼り付けるものの例 |
| --- | --- | --- |
| `config/tags/head.html` | HTMLの `<head>` 開始直後 | GTMのscript、Adobe Tagsなどです。`<script>…</script>` を含むタグ全体を貼り付けます。 |
| `config/tags/body-start.html` | HTMLの `<body>` 開始直後 | GTMのnoscriptなどです。`<noscript>…</noscript>` を含むタグ全体を貼り付けます。 |

ファイル内には最初から説明コメントがあります。**コメントの終わりの `-->` より下に、発行されたタグを貼り付けて保存します。** コメントの中に貼り付けると実行されません。`<head>` や `<body>` 自体を追加する必要はありません。

保存後に `npm run cf:deploy` を実行し、成功したら公開ページを再読み込みします。ECのMPA・SPA、静的ページ一覧、`public/lab/` に追加したHTMLに共通で挿入されます。個別HTMLにも同じタグを貼ると二重読み込みになるため、共通設定したタグは重複して配置しません。

MPAはページのHTML取得ごと、SPAは初回表示・ブラウザの再読み込み時にタグを読み込みます。SPAの画面内遷移だけではタグを再実行しません。共通タグはブラウザへ配信されるため、秘密のAPIキーやパスワードは記載しません。

## 5. サーバー側のCookieを変更・追加する

この教材では、サーバーがHTTPレスポンスの `Set-Cookie` ヘッダーでCookieを発行します。Cookieそのものはブラウザに保存されます。`config/tags/` に貼り付けるJavaScriptのCookie設定とは別です。

### 既存の検証用Cookieを変更する場合

**`config/lab.mjs` を開きます。** 初期状態では次の設定です。

```js
export const cookieConfig = {
  enabled: true, name: 'lab_fpid', maxAge: 60 * 60 * 24 * 365,
  httpOnly: true, sameSite: 'Lax', secure: 'auto', path: '/',
};
```

| 変更したいもの | 編集する項目 | 例・反映される内容 |
| --- | --- | --- |
| Cookie名 | `name: 'lab_fpid'` | `'my_fpid'` に変えると、その名前で発行します。 |
| 有効期間 | `maxAge` | 単位は秒です。30日なら `60 * 60 * 24 * 30` にします。応答ごとに期限を更新します。 |
| JavaScriptから読めるか | `httpOnly` | `true` なら `document.cookie` から読めません。読み取りを検証したい場合だけ `false` にします。 |
| クロスサイトでの送信条件 | `sameSite` | 初期値は `'Lax'` です。`'None'` を試す場合はHTTPSで `Secure` が必要です。 |
| HTTPS限定の送信 | `secure` | `'auto'` はHTTPS時だけSecure属性を付けます。公開先ではHTTPSなので付与されます。 |
| 送信対象のパス | `path: '/'` | 初期値はサイト全体です。範囲を狭めると対象外のパスには送信されません。 |
| 発行の有効・無効 | `enabled` | `false` で以降の発行を止めます。ブラウザ内の既存Cookieは自動削除しません。 |

例えば名前を `my_fpid`、有効期間を30日にする場合は、次の行に変更します。

```js
  enabled: true, name: 'my_fpid', maxAge: 60 * 60 * 24 * 30,
```

この設定は既存の検証用Cookie一つを変更するもので、二つ目を追加する操作ではありません。値はサーバーが作るランダムIDです。既存の有効なIDが送られてくれば再利用します。Adobe FPIDとの連携は未実装です。

カート・ログイン用の `lab_session` は別のCookieです。検証用Cookieの名前に `lab_session` を指定しないでください。初期設定はDomainを指定せず、アクセスしたホストだけで使います。

### 別のCookieをもう一つ追加する場合（コード編集）

**追加の発行処理は `src/app.mjs` に書きます。** 以下は、既存Cookieを残したまま、30日間の検証用Cookie `lab_custom_id` を追加する例です。手順書のサンプルであり、最初から発行されているCookieではありません。

1. `src/app.mjs` をエディタで開きます。
2. ファイル内で `headers.set('Content-Type',type);` を検索します。`async function respond(...)` の中に一か所あります。
3. **その文字列の直前に改行を入れ、次のコードを追加します。** 元の `headers.set(...)` と後ろの `return new Response(...)` は残します。

```js
const customCookieName = 'lab_custom_id';
const receivedId = cookies[customCookieName];
const customId = typeof receivedId === 'string'
  && /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i.test(receivedId)
  ? receivedId
  : randomUUID();
headers.append(
  'Set-Cookie',
  `${customCookieName}=${customId}; Path=/; Max-Age=2592000; HttpOnly; SameSite=Lax${secure ? '; Secure' : ''}`
);
```

この位置に追加すると、ログイン・ログアウトでセッションCookieを再発行した後も、追加Cookieを付けられます。`cookies`・`randomUUID`・`secure` は既存コードで定義済みなので、そのまま使えます。`headers.append` を `headers.set` に変えると既存のSet-Cookieを上書きしてしまうため、`append` のまま使います。

| 追加例で変える場所 | 反映される内容 |
| --- | --- |
| `'lab_custom_id'` | 追加するCookieの名前です。既存Cookieと重複しない名前にします。 |
| `Max-Age=2592000` | 有効期間です。2,592,000秒＝30日です。 |
| `HttpOnly; SameSite=Lax` | Cookieの属性です。初期例はJavaScriptから読めない設定です。 |

追加例はランダムIDの保存・再送を検証するためのもので、会員認証やサーバー側データとの紐付けは行いません。通常のアプリ応答に追加されますが、Worker側で先に返す413エラーなどには付きません。

### 保存して公開先で確認する

編集したファイルを保存し、プロジェクトのフォルダで実行します。

```sh
npm run cf:deploy
```

成功後、公開サイトをブラウザで開いて次を確認します。ChromeまたはEdgeの場合の例です。

1. 開発者ツールを開き、**Network** タブを選んでページを再読み込みします。
2. `/classic/` などのページのリクエストを選び、**Headers → Response Headers → Set-Cookie** に設定したCookie名があることを確認します。
3. **Application → Storage → Cookies → 公開サイトのURL** を開き、Cookieの名前・値・有効期限・HttpOnly・Secure・SameSiteを確認します。
4. 再読み込みし、有効なIDが再利用されることを確認します。`HttpOnly` のCookieが `document.cookie` に出ないのは正常です。

ローカルのNode.js版で確認する場合は、`npm run dev` をCtrl+Cで止めて起動し直します。Cloudflareのローカル版は `npm run cf:dev` で確認します。

名前やPathを変更しても古いCookieは残ります。比較時は開発者ツールで自分が追加した検証用Cookieだけを削除し、再読み込みしてください。`lab_session` を削除するとログイン・カートのセッションが切り替わります。また、追加コードを消して再デプロイしても、発行済みCookieは有効期限まで残るため、必要に応じてブラウザから削除します。

Cookie属性の仕様は[MDNのSet-Cookie解説](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)も参照してください。

## 6. CMPの同意設定を検証・変更する

初回アクセス時に同意バナーが表示されます。「すべて許可」「必須のみ許可」「個別に設定」から選びます。個別設定ではアクセス解析・広告・パーソナライズを切り替え、「この設定を保存」を押します。必須は常に有効です。

**現在はバナー・設定画面・同意内容の保存までの実装です。拒否してもCookieの発行、dataLayerイベント、追加したGTM・GA4等の送信は停止しません。** Google Consent Modeとの接続もまだありません。

### 選択内容を確認・リセットする

1. 「個別に設定」でアクセス解析だけを許可し、保存します。
2. 左下の「同意設定」に「個別設定」と表示されることを確認します。
3. 再読み込みして設定画面を開き、アクセス解析だけがオンのままであることを確認します。同じ公開URL内のMPA・SPA・静的ページでも引き継ぎます。
4. 「必須のみ許可」「すべて許可」でも保存し、表示とチェック状態を確認します。保存せず閉じた変更は反映しません。
5. 設定画面の「検証用の操作」を開き、「同意設定をリセット」を押すと初回バナーに戻ります。ログイン・カートや既存Cookieは削除しません。

保存先はCookieではなく、ブラウザの **localStorage** です。Chrome・Edgeの開発者ツールで **Application → Local Storage → サイトのURL** を開き、`exture_consent_v1` を確認できます。`analytics`・`marketing`・`personalization` の `true` は許可、`false` は拒否です。`necessary` は常に `true` です。保存日時の `savedAt` と有効期限の `expiresAt` はミリ秒の時刻です。

保存期間は初期値で180日です。期限切れは次回のページ読み込みやタブへ戻った際に判定し、未設定に戻します。同意は会員データやCloudflareのデータベースには保存しません。別ブラウザ・別の公開URLには引き継ぎません。ブラウザが保存を拒否した場合は画面に案内し、そのページ内だけで選択を保持します。

開発者ツールのConsoleでは `window.extureConsent.getState()` でも現在の内容を確認できます。未設定なら `null` です。変更時は `window` に `exture:consent-change` イベントを通知しますが、dataLayerへの同意イベント追加は行いません。

### 編集するファイル

| 変更するもの | 編集するファイル・項目 |
| --- | --- |
| バナーの有効・無効 | `public/cmp-config.mjs` の `enabled` です。`false` にすると表示を止めます。保存済みの同意内容は削除しません。 |
| 保存期間 | 同ファイルの `retentionDays: 180` です。変更後に保存した設定から適用します。 |
| 既存の同意を取り直す | 同ファイルの `version` を増やします。更新後の再読み込みで古い版の同意を未設定として扱います。 |
| 各目的の名前・説明 | 同ファイルの `consentCategories` の `label`・`description` です。`id` は保存データの識別名なので、そのままにします。 |
| バナー・設定画面の文言 | `public/cmp.mjs` です。 |
| 色・余白・配置 | `public/cmp-styles.mjs` です。 |

保存後は `npm run cf:deploy` を実行し、公開ページを再読み込みします。初回表示を確認したい場合は設定画面からリセットしてください。

## 7. 配布元の更新を取り込む

まず、次を実行して自分の編集が残っていないか確認します。

```sh
git status --short
```

以前の `feat/cloudflare-deployment` ブランチからクローンした場合は、変更がないことを確認してから、初回だけ次を実行して最新版の `main` へ切り替えます。

```sh
git fetch origin
git switch main
```

自分用の `wrangler.local.json` はGit対象外なので、そのまま残ります。切り替えに失敗した場合はそこで止め、表示されたエラーを確認してください。

`main` にいることを `git branch --show-current` で確認したら、次を1行ずつ実行します。

```sh
git pull --ff-only
npm ci
npm run cf:deploy
```

ファイル名が表示される場合や `git pull` が失敗した場合は、そこで止めてください。自分の編集をバックアップし、配布元の管理者へ取り込み方法を確認します。既存の変更を削除してやり直す必要はありません。

自分用の `wrangler.local.json` はGit対象外なので `git pull` では上書きされません。配布元の更新でCloudflare設定の変更が案内されている場合は、その指示に従って自分用設定にも反映します。

同じアカウント・Worker名への再デプロイでは、会員・カート・注文データが保持されます。Worker名を変更すると別サイト・別データになり、元のWorkerも残ります。単にサイトを更新するときは `name` を変えません。

## 変更後にうまく動かない場合

デプロイコマンドがエラーで終わった場合は、エラーに表示されたファイル名と行番号を確認します。編集時に引用符・カンマ・括弧を消していないか見直してください。必要なら編集前のコピーに戻し、再デプロイします。

デプロイが成功しても公開ページを開けない場合は、コマンド末尾の公開URLと、実際に開いているURLを照合します。詳しい切り分けは[導入手順書の「困ったとき」](cloudflare.md#困ったとき)を参照してください。
